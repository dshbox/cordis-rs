# Cordis v3 upstream parity ledger

This ledger is the v3-owned evidence record against Cordis TypeScript at
exact commit `8cc9e33fab69e2d0476d126baaf2acb24e6a6ab4` — the pin. It is
normative for upstream relationships: it owns the parity/divergence
classification of every pinned fact and the evidence for it. It does not own
v3 rules; each row's owner column links the one canonical v3 document that
owns the conclusion the disposition summarizes.

Upstream paths below are relative to the pinned checkout. The pin is the only
upstream architectural authority this ledger recognizes; upstream head is
irrelevant to every row. The ledger is self-contained: each row cites the
pinned source directly, and evaluating a row requires no other ledger, branch,
history, or ticket.

## Authority and verification

- **Exact pin.** Every citation names a path and line range inside commit
  `8cc9e33fab69e2d0476d126baaf2acb24e6a6ab4` of the Cordis TypeScript
  repository. No row cites any other revision, and no citation is delegated to
  another document.
- **Positive claims** were read at the cited source and, where named, test
  ranges of the pinned checkout.
- **Absence claims** cite the complete relevant declaration or public-operation
  surface; the identifier or capability was additionally checked by
  repository-wide search in the pinned checkout. "Absence" therefore means no
  counterpart exists in that exact evidence scope, never that an older document
  omitted it.
- **Comparison target** is the final v3 architecture as published in
  [docs/v3-architecture.md](v3-architecture.md) and its normative set —
  [CONTEXT.md](../CONTEXT.md), [ADRs 0028–0038](v3-architecture.md#decision-index), and the
  [public-interface inventory](v3-public-interface.md) — not any current or
  historical implementation state, which this ledger never cites.

## Relationship vocabulary

Each row carries exactly one v3 relationship:

- `parity` — the pinned behavior is v3 behavior; any strengthening (for
  example concurrency arbitration) preserves the observable contract.
- `representation rework` — the same semantic capability survives in v3 with a
  different representation or mechanism.
- `behavioral divergence` — v3 deliberately behaves differently.
- `absence` — the row's capability has no v3 counterpart, or the row records a
  v3 addition with no upstream counterpart.

An `absence` row also carries exactly one absence direction: `upstream-only`
(the pinned capability is deliberately absent from v3) or `v3-only` (the v3
capability has no pinned-upstream counterpart, so omitted upstream utilities
and v3 additions such as era replacement are never conflated). Non-absence
rows mark the direction `—`.

## Row schema

`ID | pinned-upstream fact (path:line at the pin) | v3 relationship | absence
direction | concise v3 disposition | canonical v3 owner`

Row IDs are stable and sectioned by upstream subsystem. The disposition states
the final v3 position concisely; the owner links the single canonical v3
document that owns the underlying rule or declaration. This ledger owns the
comparison, not the v3 rule.
